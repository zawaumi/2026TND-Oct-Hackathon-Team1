## 3. ブランチ
`main`はデプロイ可能、`feat/*`で1Issue単位の短命PR、`fix/*`で修正。PRでは受入条件と自動テストを確認し、コードレビューは最低1名。APIの変更は`contracts/openapi.yaml`を同時更新。

## 4. CI/CD
- Frontend（`.github/workflows/web-ci.yml`）：Node.js 26（`apps/web/.nvmrc`）→`npm ci`→`npm run lint`→`npm run typecheck`（`next typegen && tsc --noEmit`）→`npm run build`（静的出力）。`apps/web/**`を変えたPRと、`main`へのpushで動く。Firebase Hostingへの配備は#56で追加する。
- Backend：依存解決→Django check→pytest（Postgres service）→Container build→Cloud Run deploy。
- Deploymentの本番シークレットはGitHub ActionsのSecret/Google Cloud Workload Identity Federation等で管理し、固定サービスアカウント鍵の配布を極力避ける。
- 変更箇所だけのCIに最適化する前に、初期は毎PR両ジョブの成功を必須にする。
- `main`へのマージはCI成功が条件。リリースはGit tagとアプリのバージョン記録を残す。

## 5. 実装順序とデモ縮退計画
1. Googleアカウントでログイン（Firebase）→DRF`/users/me/`認証。
2. 固定教材をDBに投入→最初の1小単元のUIを実装。
3. JevをモックにしてDeepSeek質問を表示。
4. 逆にDeepSeekをモックにしてJevの判定統合を試験。
5. 最小SkillExecutorの数学的正解を独立検証→MasteryEvidence→React Flow連携。
6. 最終レポート・アバター・デプロイ・品質検証。

**縮退プラン**：外部AIが障害のときも、架空の既定データ＋決定的な解法ステップで主要機能を説明できる審査用デモモードを準備。ただしデモモードを本番AIの実演と偽らない。

## 6. 発表の論点
独自性（ぴあ友に教える）、教育的合理性（学習指導要領・国研）、制約付きAI（DBが状態管理し勝手にMASTEREDにしない）、UI（可視化）、安全性（情報最小化・不正入力対策）、実験（DeepSeek単独 vs Jev）を均等に説明し、未検証値は結果と区別する。自由学習と探究学習は「今後の拡張」として説明する（ADR-013、ADR-019）。
