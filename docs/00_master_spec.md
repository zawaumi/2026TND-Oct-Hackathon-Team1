# ぴあとも 総合仕様書

**文書ID** PT-SPEC-001 / **版** 1.1 / **作成日** 2026-10-31 / **改訂日** 2026-11-08 / **対象** TND 秋のハッカソン2026

> **位置づけ**：本書は2026年10月31日までの企画・設計上の合意と、11月7日の決定（[08](08_decisions_and_open_items.md) ADR-013〜023）を統合したベースラインであり、完成したソフトウェアや検証済み教育効果を主張するものではない。確定設計とMVP限定仕様、暫定設計を区別する。用語は[用語集](glossary.md)に従う。

## 1. 製品概要

### 1.1 コンセプト
「ぴあとも」は、中学生・高校生のユーザーが同年代のAI生徒「ぴあ友」に学習内容を教え、自身の説明を言語化・改善しながら理解を深めるWebアプリ。ぴあ友は知識グラフに基づいて段階的に知識を獲得し、ユーザーが出した問題を解き、その結果によって成長する。ユーザーには説明力スコアのレポートと、ぴあ友の習得の可視化を提供する。

### 1.2 目的 / 非目的
- **主目的**：教える学習（ピアティーチング）を通じた理解の深化・復習・自己説明の促進。
- **副目的**：国の教育課程・評価参考資料に沿った小単元選択、適応的質問、明確な形成的フィードバック。
- **非目的**：学校での正式な3観点評価・評定を自動確定すること、教員向け管理機能、何でも解ける汎用AIチューターを作ること。

### 1.3 想定利用者
- 中学生・高校生（日本語UI）。学年は単元推薦とAI初期知識に使用し、学力や優劣を決めつける用途には使用しない。
- 未成年利用を考慮し、原則として氏名・学校名・住所・正確な生年月日を取得しない。
- 初回公開はハッカソン用限定MVP。一般公開前に同意・AI事業者利用規約・削除運用等を再検証する。

### 2.2 拡張（P1）
- 自由学習：任意テーマ→DeepSeekが仮のLessonSpecを生成→ユーザー確認→私有・暫定知識グラフへ保存。
- 典型的誤解のパターン、ノード点灯演出、学習推移、より詳細な評価根拠、データエクスポート。
- 自由学習は最終発表では「今後の拡張」として説明する（ADR-013）。

### 2.3 将来機能（P2）
全教科・全学年の体系的教材、自動概念グラフ統合、高度なRiveアバター、SSR等を利用したサーバーレンダリング、幅広い自然言語演習の厳密自動採点、匿名のお試し利用（ADR-016）、ユーザー本人の推定習熟度の表示（ADR-018）、教員向け管理（今回非対象）。

探究学習は「課題設定→情報収集→整理・分析→まとめ・表現」を支援する構想として残し、今回は実装しない（ADR-019）。一般的な正誤のない内容で習得済みを安易に確定しない。

## 3. 学習モード
| モード | 教材の起点 | 評価・習得 |
|---|---|---|
| 単元学習（MVP） | 中学校：平成29年告示／高校：平成30年告示の学習指導要領 | 国研の教科別参考資料を参照したルーブリック。検証可能な演習から習得を確定 |
| 自由学習（P1） | 利用者のテーマ。AI生成内容は「暫定」と明示 | 検証済み概念へ無断統合しない。主に形成的フィードバック |
| 探究学習（構想。今回は実装しない） | ユーザーが課題を設定 | 根拠・多面性・検討過程を評価し、単純な正誤・習得確定と区別 |

### 3.1 教材分類
「校種→教科/科目→領域/内容（指導要領の正式な分類）→単元→小単元→必要ならさらに細分化」のように表現。**単元・小単元の名称と細分化はアプリ独自の教材設計**であり、公式分類そのものと混同しない。高校は「数学Ⅰ／数学A」など科目を基準にし、履修学年を全国共通で固定しない。小単元は複数選択して1つのLearningSessionにできる。

### 3.2 初期教材範囲
中1数学「等式の性質」「方程式の解法」「移項」「方程式の利用」のうち、定義・例題・解法ルールが検証できた部分に限定。数学Ⅰ・数学A等は設計上対応可能とし、初期にすべて提供することを必須条件にしない。

## 4. ぴあ友の知識・状態管理

### 4.1 初期設定
AIのキャラクターは同年代で親しみやすい。一般的な学年相応の前提知識を持つが、**現在教える対象の小単元は未習得**とする。既に別の授業で獲得した概念は継承する。表情や性格は知識状態と独立した表現レイヤー。

### 4.2 概念グラフ
- `Concept` は教科横断で一意に扱える知識・技能ノード。`Lesson`と多対多。
- 前提関係は`ConceptPrerequisite`に保持する有向非巡回グラフ（DAG）。一般的な関連は別エッジ型とし、前提関係と混ぜない。
- 複数単元が同じ概念を参照できる。前提を習得しても下流の概念を自動で習得させない。
- 検証済み公開概念 `CURATED` と個人の暫定概念 `PRIVATE` を区別。公開への昇格は人手でレビュー。

### 4.3 習得段階
未習（`UNKNOWN`）→ 説明済み（`INTRODUCED`）→ 練習中（`PRACTICING`）→ 習得済み（`MASTERED`）。
- `INTRODUCED` は説明済み。LLMの「理解した」発言では確定しない。
- `PRACTICING` は明示的に説明された技能を練習できる段階。許可された演習で使えるため、初回正答へのデッドロックを防ぐ。
- `MASTERED` は**対応問題が検証可能で、解法・使用技能を確認でき、MasteryPolicyを満たした場合のみ**。Jevの高スコアだけでは確定不可。
- `reset_epoch` / `knowledge_version` によってリセット前の根拠を再使用せず、古いAI応答による復活を防止。

### 4.4 難易度別の初期MasteryPolicy（製品仮説）
| レベル | 検証済み正答数 | 多様性 | 条件 |
|---|---:|---|---|
| 基礎 | 1 | 1形式 | 正答・解法検証必須 |
| 標準 | 2 | 異なる2形式 | 同一テンプレート反復を除外 |
| 応用 | 3 | 2形式以上・うち応用1題 | 原則として段階検証 |

これらは**教育的に妥当性が確認済みの習得閾値ではない**。予備実験と運用データで調整する。

## 5. 授業進行とAIの役割

### 5.1 1ターンの処理
1. Firebase IDトークンを検証し、本人が所有する授業（セッション）か確認。
2. `request_id` と本文ハッシュを検証し、受付レコードを保存。重複は再計算しない。
3. 現在の教材・知識状態と`knowledge_version`を取得し、短いトランザクションを終了。
4. 入力の形式と不正命令・個人情報混入を検査。必要なら`ALLOW` / `DATA_ONLY` / `REJECT`に振り分ける。
5. 判定が必要な説明のみJevに問い合わせる。Jevが分類/スコア候補を返す。
6. DRFが使用可能技能・質問方針を決定。DeepSeekが制限付きJSONを返す。
7. DRFがスキーマ・Action・概念ID・数学的ステップ等を検証。確認不能なら定型応答に置換。
8. 行ロック付き短いトランザクションでバージョンを確認し、本人用状態・最小限の評価根拠を保存。
9. Next.jsへ応答を返す。ブラウザが画面上の会話履歴を管理。

### 5.2 責務の分離
| コンポーネント | 許可される仕事 | 禁止事項 |
|---|---|---|
| DRF | 状態遷移、習得・採点確定、認証認可 | AIの曖昧な主張のみを根拠にMASTEREDにしない |
| DeepSeek | 質問・対話表現・自由学習の仮教材案 | 任意のDB操作、未許可技能を用いる検証不能な解答の確定 |
| Jev | 構造化分類、観点別評価候補 | 正解保証、教育上の正式評定、DB更新 |
| Skill Executor | 許可技能だけを用いる有限の数学的操作 | 汎用数式ソルバーで未習得技能を迂回すること |
| SymPy | 数式・解・各ステップの独立検証 | 非信頼入力を無制限に式として評価すること |

### 5.3 説明・質問方針
DRFが`ASK_WHY` / `REQUEST_EXAMPLE` / `CHECK_PREREQUISITE` / `CONTRAST_CASES` / `ATTEMPT_EXERCISE` / `EXPLAIN_BACK`から方針を選択し、DeepSeekが自然な1質問を生成。無理な複数質問や知識と矛盾する発話を避ける。ALTER-Mathは教育上の参考発想であり、API・コード依存はしない。

## 6. 出題・解答・検証
- ユーザーが文章またはMathLiveによるLaTeX数式を入力できる。
- `Exercise`は`VERIFIED` / `PROVISIONAL` / `UNSUPPORTED`の検証可能性を保持。
- 数学MVPでは対応範囲を一次方程式の限定パターンに設定。サーバーの安全な構文・演算子ホワイトリストと計算量制限を必須にする。
- Skill Executorは前提・状態から許可技能を求め、検証済みの式変形を列挙・選択。汎用SymPyは**正誤の独立検証**であってぴあ友の隠れた万能解法器ではない。
- 解答正誤、各ステップ妥当性、技能使用、問題形式の重複、知識世代を確認してから`MasteryEvidence`へ記録。
- 自由記述はAIによる暫定評価を基本とし、形式的に検証できない内容を自動でMASTEREDにしない。

## 7. 学習評価
- 国立教育政策研究所の教科別「指導と評価の一体化」のための資料を参照し、**知識・技能／思考・判断・表現／主体的に学習に取り組む態度**を評価規準の土台とする。
- 説明力スコアはぴあとも独自の参考指標（カラオケの採点のように、複数の観点の割合で示す）。観点は**正確さ40・論理性30・分かりやすさ30**の3つ（合計100）。配点は仮の値で、版管理する（ADR-015）。
- ぴあ友の質問への対応は独立した観点にせず、3観点それぞれの中で評価する（例：質問への答えに誤りがないか＝正確さ、根拠を示して答えたか＝論理性、つまずきを言い換えや例で補えたか＝分かりやすさ）。
- 3観点は国研の「知識・技能」（正確さ）と「思考・判断・表現」（論理性・分かりやすさ）に対応させる。「主体的に学習に取り組む態度」は長期的な根拠が必要なため、MVPの説明力スコアでは扱わない。
- レポートでは、ユーザーの説明力スコアと、ぴあ友の検証済みの習得を**別のデータ・別の画面ラベル**で表示する。ユーザー本人の推定習熟度はMVPでは表示しない（ADR-018）。
- 根拠が足りない観点は評価保留とする。会話回数や発言量だけで採点しない。
- `Rubric` / `Criterion` / `Evaluation` / `CriterionResult`を版管理し、何を根拠にどの尺度で判定したか追跡可能とする。ただしプライバシーのため会話本文の根拠は原則長期保存せず、会話内の説明箇所は端末内でのみ表示する。

## 9. 技術スタック / デプロイ
- モノレポ（GitHub）。`apps/web` Next.js + TypeScript + Tailwind（Node.js 26、`apps/web/.nvmrc`）、`apps/api` Django REST Framework + Django ORM。
- UI：MathLive入力、KaTeX表示、SVG + Motion for React、React Flow。
- Firebase Authentication（MVPはGoogleアカウントでのログインのみ。ADR-016）、Firebase Hosting（Next.js静的出力）、Firebase Hostingの`/api/**` Cloud Runリライト。
- DRFをCloud Runで提供、PostgreSQL（本番はCloud SQL等、費用・配置は未最終確定）。GitHub Actions、Docker ComposeのローカルDB。
- DeepSeekは自然会話、Jevは構造化判定。APIキーはサーバー秘密管理。nginxは使わない（本番はFirebase Hostingが転送を担う。ADR-014）。
- 静的Next.jsでは未事前生成の動的ルートやSSR、Server Actionsを前提にしない。学習画面を固定パス`/study/?session=...`等にする。
- Hosting経由のCloud Runリライトは60秒の上限を考慮。MVPは非ストリーミング応答＋進捗UI。未検証のAIの生出力はストリーム配信しない。

## 10. セキュリティ・プライバシー

### 10.1 権限境界
すべての個人APIはFirebaseトークン検証＋Djangoユーザー特定＋オブジェクト所有者認可。クライアントの`user_id`や`peer_id`を本人証明に用いない。重複送信防止は`(session, request_id)`一意制約。`knowledge_version`と行ロックで競合を防止。サーバーへモデル生出力による状態更新権限を与えない。

### 10.2 プロンプトインジェクション対策
- 形式検査（文字数・制御文字・型・数式構文）→ルールによる兆候検知→`ALLOW`/`DATA_ONLY`/`REJECT`→信頼できない入力の分離→構造化出力検証→DRFの最終状態検証。
- 役割偽装、採点100点指定、全概念MASTERED命令、システムプロンプト開示要求、自由教材への指示埋め込み、偽JSON等を脅威として想定。
- `DATA_ONLY` は引用や教材文として処理し、操作命令として使わない。正当なセキュリティ授業内容を過剰拒否しない。
- **正規表現だけでは防御できない**。防御の主軸はAIに権限を渡さないこと・スキーマと状態更新の独立検証・検証不能時の定型フォールバック。未知の攻撃には残余リスクがある。

### 10.3 データ最小化
- 初期登録はFirebase UID（内部識別用）、ニックネーム、校種、学年のみ。氏名、学校名、住所、生年月日、Googleプロフィール全文は原則不要。
- 会話全文は原則サーバーDBに保存しない。ブラウザのメモリ内に置き、任意の端末内保存は明示的に選択させる。共有端末のリスクと他端末へ会話が同期されないことを説明する。
- AI呼び出しには必要な直近入力と教材のみ送信。UID、電子メール、認証トークンは送らない。入力文自体に個人情報が含まれる場合があり、検知・注意喚起は完全ではない。
- 習得根拠は概念ID、問題形式、正誤、検証方法、世代番号など必要最小限。生の回答や途中式も不要な長期保存を避ける。
- Cloud Logging等では会話本文・認証トークンを記録しない。

### 10.4 退会・保持期限（*設計上の目標*）
| 対象 | 目標 |
|---|---|
| 退会リクエスト | 即時アクセス停止、削除処理を記録 |
| 稼働DB・Firebase認証情報 | 24時間以内に削除（稼働確認後に公表するSLO） |
| 通常アプリログ | 7日以内の短期保持を目標 |
| バックアップ | 最大30日以内の保持を目標。採用サービスの実設定を検証 |
| 端末保存 | 当該端末で利用者が削除可能。別端末分はサーバーから強制消去を保証しない |
| 外部AI事業者の保持 | 契約・提供規約に従う。未確認のため保証をしない |
| 必須監査ログ | Cloud Logging `_Required` 等の保持期間は別途開示（Google Cloudで400日など） |

法令・事業者の要件により例外があり得るため、**「すべてのコピーが退会直後に完全消去される」とは表示しない**。削除ジョブは再実行可能にし、バックアップ復元時も削除済みアカウントが復活しない対策を設ける。

## 11. 性能・信頼性の初期目標
- 対話応答はMVPではJSON完成後に表示。AIごとに明示的タイムアウトを設定し、非検証の結果は表示しない。
- 応答時間P50/P95、Jev時間、DeepSeek時間、フォールバック率、検証失敗率、1授業の費用を観測。
- Cloud Run初期案：1 vCPU、1 GiB、同時8、最大2、通常最小0・発表時1を検討。**負荷試験前の仮値**。
- Firebase Hosting経由ではHTTPの60秒上限に注意。DBトランザクション中に外部AIの応答を待たない。
- `request_id` により二重課金・二重更新を減らし、期限切れ処理中ジョブの復旧・再送を設計する。
